# 公司官网岗位情报系统：方案与开源评估

研究日期：2026-09-08。状态：方案评估，未部署、未启用每日任务、未登录招聘账号、未投递。

## 一、结论

这个项目应当成为你的“公司与职业机会研究系统”，而不是 BOSS 批量搜索器。

主链路是：**行业与公司发现 → 官方招聘入口核验 → 岗位新增/变更监测 → 个人证据匹配 → 材料准备 → 经授权投递 → 反馈复盘**。

建议保留当前职场项目作为主项目，优先评估复用 Offer Harvester 的公司官网采集和岗位目录模块；按需补充 ATS 适配器。不建议直接部署整套开源求职控制台，也不建议从零重写所有采集器。

本轮已下载四个仓库、核对代码和许可证，并执行离线测试。没有证据证明其中任何项目已经在你的目标公司集合上跑通完整每日采集。代码存在、测试通过和真实网站可用是三件事。

## 二、目标与核心矛盾

目标不是“收集最多岗位”，而是让你尽早发现值得尝试、有来源可核验的机会，同时理解市场正在购买哪些能力。

最大的矛盾是：既要跨行业发现机会，又要证明信息真实、及时、与你相关；不能为了覆盖数量，把猜测公司、过时页面、丢字段的 JD 和模型分数当成可靠结果。

本版以你的最新表述为准：AI 优先，但不限销售或管理职称；BD、商业化、客户成功、业务型售前、实施等可探索。技术型 FDE 单独判断生产编码和交付门槛。现有个人画像仍写着“管理优先”，实施时应把“事实档案”和“可变求职偏好”分开，本轮未改写原画像。

- `00_行业资料集/AI产业链公司资料集.csv` 有 121 个不同公司/品牌名称、12 个细分赛道。名称不是已归并的法律实体，也不等于 121 家当前在招公司。

- 已有个人事实画像、简历素材和岗位汇总输出可以继续使用，不必重建另一套个人资料库。
- 现有 BOSS 路径仍受人工优先/风控恢复规则限制。打开本地安全入口不构成采集成功，也不应成为公司官网采集的前置依赖。

### 必须处理的代码问题

1. **Offer Harvester：公司采集器没有输出薪资字段。** `cli/src/providers.ts` 的 `Job`/`makeJob` 不包含薪资；通用目录即使有 `salary_raw` 列也接不到此模块的数据。不能只加一列展示就算完成。
2. **Offer Harvester：固定同源请求间隔只有约 400ms。** `cli/src/http.ts` 不是你要求的 10–20 秒节奏。应改为全局队列加每域策略，收到限制立即暂停。robots 可读或未禁止不代表接口获得无限制访问许可。
3. **Offer Harvester：有限查询不是整个公司招聘站的完整快照。** 必须把 query、页数、截断状态与运行记录一起保存；关键词结果中消失不能推断职位下架。
4. **Offer Harvester：多来源职位状态需修正。** `automation/apply_bot/job_catalog.py:_effective_state` 遇到任一来源 closed 就返回 closed，即使另一个来源仍 open。合并 BOSS 和官网时应保留每来源状态，并优先复核有效官方源。
5. **ats-jobs：JD 和薪资会丢字段。** Lever 只取简介，没有拼接职责/任职要求列表；Ashby 请求可含薪资但解析未保留，也未过滤 `isListed=false`。
6. **ats-jobs：更新时间被当作发布时间。** Greenhouse `first_published || updated_at` 不能证明新岗位。首次采到、首次发布、再次发布、更新时间要分开。
7. **ats-jobs：访问和完整性控制要改。** 默认会并行猜测 ATS，分页也并发；部分失败页被跳过但没有完整快照证明。`Retry-After` 等待被上限压到 5 秒，不能照搬。
8. **JobSync：中文与薪资链路不完整。** `ats/rank.ts` 的标题切词只保留拉丁字母和数字，纯中文标题可能在 AI 读取前漏掉；Ashby mapper 不映射薪资，persist 也不传薪资。其匹配提示词把高分关联到高面试可能性，必须改为可解释证据覆盖，不作概率承诺。
9. **job-alerts：局部失败会影响其他状态。** 拉取层把某源失败折叠为空数组，汇总层只在全体结果为空时跳过删除；一家公司成功、另一家失败时，后者职位可能被当成移除。必须按来源隔离成功完整快照。
10. **Offer Harvester：配置上限与错误隔离不适合直接导入旧库。** `commands/search.ts:loadCompanies` 上限 100 家，且筛选启用公司前校验全部 URL。当前 121 个标签不能直接导入；不支持的入口应进入待核验队列，不能阻塞所有来源。
11. **Offer Harvester：robots 异常不能一概视为许可。** `http.ts:check` 对未识别为验证页的 HTML 按空规则处理。应保留“不明确”的状态、停止该源并核验，而不是将任何 HTML 回退页当作允许访问。

以上是选型审查，不是完整安全审计。Bun/Next.js 整套应用未安装和启动；未运行投递模块；未向外部模型发送简历。

- 独立构造 8 项契约探针：4 项复现实际缺口，4 项验证 Offer Harvester 的职责保留、分页截断、失败分类和 robots 拒绝行为。见 [探针结果](evidence/contract-probes.json)。

## 五、推荐架构

### 1. 公司发现层：先有值得关注的企业集合

以现有 121 个公司/品牌标签作为历史种子，重新归并母公司、品牌、业务部门和雇主主体。每周扩充，而不是让模型凭记忆生成“行业前十”。

赛道按与你的机会关系组织：基础大模型/MaaS、云与企业 AI、营销获客/广告 AI、企业 Agent/流程自动化、汽车与零售数字化、智能硬件与行业方案。行业边界开放，优先度由机会和证据决定。

“头部/腰部”必须带依据与日期：分赛道查看客户覆盖、可核验营收/市场地位、产品商业化和规模资料。融资只作信号，不等于排名。证据不足写“成长型候选/层级待核验”，不能硬排 Top10。官方网站自述的领导地位也不能单独当作独立排名。

每家公司至少保存：名称与别名、母公司/雇主主体、细分赛道、产品卖给谁、与你相关的理由、分层证据、官网、所有社招入口、ATS 类型、入口归属证据、最后核验时间、采集方式、访问限制、来源健康。

每周可从官方产品与客户案例、公司新闻、行业研究和可信投资机构组合名单中发现新公司，再回到官网确认；模型只提候选与解释，不代替证据。

### 2. 来源采集层：官网优先，招聘平台补充

优先序：企业正式职位接口/订阅 → 官网公开职位页 → 经确认的招聘系统页面 → 授权的招聘平台浏览/人工导入。

Greenhouse 的公开 Job Board GET 不要求认证；Ashby 公开岗位接口可按参数返回薪资；Lever 有公开 postings 文档。这与企业 HR 内部接口不是一回事。参见 [Greenhouse 文档](https://docs.greenhouse.io/job-board.html)、[Ashby 文档](https://developers.ashbyhq.com/docs/public-job-posting-api)、[Lever 文档](https://github.com/lever/postings-api)。

飞书、Moka、Workday 等网页使用的接口，需要逐来源验证公开访问边界、页面一致性、分页和失败行为；开源代码称其“公开”不等于平台承诺长期支持。禁止绕验证码、签名鉴权、WAF 或访问拒绝。不得因库带有解码逻辑就默认批准所有来源。

不把持久登录端口作为整个项目的根基。多数公开职位阅读可以不登录；申请或某些受限详情才需要平台会话。登录凭据不进入公司库或 Git，浏览器不反复启动安全入口。

### 3. 证据与变化层：知道它从哪里来，发生了什么

数据库建议 SQLite：公司、来源、职位实体、各来源职位记录、快照、运行日志、变更事件、匹配评估、材料版本和申请记录分别建表。

职位保存：原始标题、雇主、部门、国家/城市/地点、远程范围、招聘类型、薪资原文、币种/周期/底薪或 OTE、JD 职责与要求、经验学历、岗位链接/申请链接、来源岗位 ID、发布时间语义、首次/最近看到时间、详情完整性和原始证据路径。

原始网页/JSON 留在本地审计存储，脱离模型摘要保存。遵守来源使用与保留限制，不公开分发大批完整 JD。每次摘要指回来源和快照。

关键规则：

- 首次运行建立基线，旧职位不报成“今天新增”。以后分别标记首次发现、薪资/JD/地区变更、来源明确关闭、待复核和重新开放。
- `first_seen_at` 不是 `published_at`。Ashby `publishedAt` 的文档含义是最近一次发布，也应保留来源语义。
- 没公开薪资就写“未披露”，不从同公司、旧岗位或行业均价补写。
- 任何超时、429、验证页、字段异常、分页截断都使该源本轮状态成为失败或不完整，不用其缺失记录推断下架。
- 无明确关闭证据时，至少经过两次成功完整且同范围的快照缺失，再进入待关闭复核；必要时核对详情。大幅条数骤降先触发来源异常检查。
- 主键使用来源+租户+岗位 ID。跨源只做候选重复关联，不按“公司+岗位名”粗暴合并不同城市/职级；保留各源薪资和状态冲突。
- 新增通知需要幂等事件 ID。重跑不重复提醒；推送失败可重试通知，但不重抓整个站点。

### 4. 岗位筛选层：按组织需求和证据，不只看关键词

先读取个人事实档案，再自上而下拆解岗位使命、服务对象、核心产出、客户/决策链、协作、指标和门槛。明确“直接证据、可迁移证据、真实缺口”，再决定是否推荐。

召回词覆盖中英文：销售/KA/大客户/BD/商务拓展/商业化/生态/渠道、Account Executive/Account Manager/Partnerships/GTM/Business Builder、售前/解决方案/客户成功/实施顾问/Solutions Consultant/Sales Engineer/FDE。关键词只负责找候选，最终以 JD 的业务职责为准。

你的汽车行业客户经营、10 人带队、经营复盘和 AI 工具落地，是可迁移依据；不等于已有大模型合同、客户生产 POC 或生产级 FDE 编码经验。210 商户保持个人口径，AI 提效保持个人测量口径。

薪酬规则：人民币月薪上界达到 20K 即入候选，15–30K 合格；底薪与提成/OTE、月薪与年包分开。只报年薪或外币时保留原文，折算必须显式标注假设与汇率日期，不能直接当作月度底薪。未披露但业务高度相关的官网岗位进入“薪资待确认池”，不直接丢弃。

匹配先查硬条件与证据完整性，再评估能力覆盖：80 分以上且无未解决硬门槛、JD 完整、岗位主线一致，才可建议沿用对应基础简历；有可迁移优势的岗位进入探索池。分数不是通过率，不以自动高分证明胜任。薪资、城市和工作资格的未知单独展示，不隐入总分。

### 5. 输出层：不用先建控制台

日常通过当前对话和报告交付三种视图：

1. **公司雷达**：值得关注的公司、为什么适合、官网/招聘入口、来源是否可用、最近职位变化。
2. **AI 优先机会表**：公司、岗位、薪资、城市/地点、职责与门槛摘要、直接/迁移证据、缺口、链接、日期语义、是否需改简历。
3. **20K+ 薪酬机会表**：按你定义的区间重叠筛选，单列薪资未披露池；同一职位可以同时出现在两表，底层只存一份实体。

每份日报显示已配置/成功完整/失败/未扫描来源数，以及新增、变化、去重数量。不能只说“未发现岗位”而隐去“来源没打开”。低相关或未变化不反复推送，但运行记录可查。

### 6. 材料与投递反馈层：后接，不抢占当前建设重点

保留你的自上而下简历规则和事实边界。需要新的事实才集中询问，不凭 JD 补造经历。岗位、画像、评分规则、简历版本和沟通文本互相绑定。

首次阶段只生成候选、材料建议和申请入口。启动真实投递前，再确定渠道、材料、每日上限、是否允许发起沟通以及需逐次确认的表单问题。

“已打开”“已沟通”“已发送附件”“申请确认提交”“招聘方回复”“面试邀约”分开记录。必须取得可见回执后才能记已投递。未经确认不接受 Offer，不替用户回答未知薪酬、离职时间或法律声明。

反馈按岗位方向、城市、公司层级、来源、简历版本分组；比较相同观察窗口的申请→回复→面试漏斗。未读/尚在等待不立即当拒绝；小样本不能断言某版简历导致面试率提升。

## 六、模块分工与依赖

这是职责拆分，不要求六个 Agent 同时运行。采集用确定性代码，研究/判断用 AI，避免多窗口同时访问同站。

| 模块 | 输入与关键问题 | 输出与验收 | 依赖/风险 |
| --- | --- | --- | --- |
| 行业研究 | 历史公司库、公开行业证据；哪些公司值得关注 | 带证据的公司分层与新增候选 | 可与画像校验并行；防虚构排名 |
| 入口核验 | 公司官网；招聘域名属于谁 | 归属链、ATS、访问方式和限制 | 依赖公司身份；防同名误认/旧地址 |
| 采集监测 | 已批准来源；是否读全、是否变化 | 原始快照、职位、事件、健康日志 | 依赖核验；防限流、丢页、误下架 |
| 岗位评估 | 完整 JD、真实画像、偏好 | 能力证据映射、推荐/探索/待确认 | 依赖完整采集；防关键词漏召回/虚假分数 |

Skill 只封装规则、输入输出和验收，不承担数据库或可靠调度。初期合成“公司发现与核验”“岗位采集与汇总”“证据匹配与材料”三个流程即可。

## 七、部署方式

### 推荐：先本地验收，再部署公开情报采集

**试点阶段**：在现有 Mac 本地运行 CLI、SQLite 与审计文件。沿用 Node 主项目，采集模块可经评估移植为 TypeScript 编译输出；目录层可复用现有 Python/SQLite 路径。生产不使用本轮研究用的实验性内存转译。

不启动额外公开端口，不加载日常 Chrome Cookie，不要求装新控制台。手工跑完 10–15 家公司样本后再决定任务调度。Mac 关机/睡眠会影响本地定时采集，不能承诺离线电脑持续抓取；浏览器任务还依赖桌面可用状态。

**稳定阶段**：如需电脑不开也监测，使用一个小型常开服务器/容器执行公开来源采集、数据库备份和通知队列。普通 HTTP 采集可先按 1–2 vCPU、2–4GB 内存做容量试点，这是起始预算，不是已压测规格。大量浏览器渲染需另算，初版不采用每站常驻浏览器。

推荐混合隔离：服务器只保存公开公司/JD 数据；个人履历、联系方式、简历、招聘账号会话和投递权限保留本地。云端 AI 匹配若会传出个人资料，需你另行确认；自托管 Web 应用不等于调用外部模型时数据仍留本地。

调度建议（尚未设置）：核心 20–30 家每天两轮，扩展公司每天一轮，每周一次新公司研究与失效入口复核。可以先按北京时间 09:00/21:00 采集，次日 08:30 汇总；公开网页不是必须夜里打开浏览器才能采集。

同源请求默认串行，相邻浏览器打开/搜索至少间隔 10–20 秒，接口也由来源策略限制；平台要求更慢时从严。初次小流量试点，有 403/429/验证码就停该源并报告，不轮换代理、账号或反复刷新。

部署至少包括：固定依赖版本/commit、单实例任务锁、超时与有限重试、严格遵守 Retry-After、失败队列、完整性校验、SQLite 事务备份与恢复测试、日志轮转、来源失败通知。只通知有价值的新机会和需处理的异常，避免每天制造无信息通知。

如以后直接试用 JobSync，不能照抄当前 Compose：应生成真实密钥、限制监听到本机或受控入口、固定镜像版本、审查 MCP 和模型出站设置。它当前配置公开映射 3737 且含密钥占位值；本轮没有启动。

## 八、实施顺序与验收

1. **建立真公司库**：先完成 30 家与你相关的候选企业核验，至少覆盖基础模型、企业 AI、营销获客、行业数字化。每家有官方入口或明确的“未找到/访问失败”，不编补网址。
2. **打通代表来源**：先做 10–15 家，覆盖飞书、Moka/自定义站、公开 ATS 和普通官网页；逐条抽查标题、地区、完整 JD、薪资原文和链接。受限来源允许被明确标为不可自动读取，不以绕过限制换覆盖。
3. **做增量而非重复搜索**：验证首次基线、重复运行、JD 变化、薪资变化、局部失败、分页截断、下架与重开。连续试运行一周，失败可解释且不误报“无岗位”。
4. **接画像与双视图**：提供 AI 优先和薪资优先表，人工复核首批 20 个候选；检查“Business Builder 等无销售字样角色”没有漏掉，“Sales Engineer”也没有被一概判为适合。
5. **最后接投递和反馈**：单独确认授权后开始小批量；先保证岗位、材料与提交回执正确，再考虑扩量。

不能仅按日期验收。主要门槛是：每条推荐都有来源链接和详情证据；薪资未知不被填零或猜测；未完整扫描不关闭职位；重跑不重复报新；真实缺口不被改写成履历；可按公司解释为什么推荐或没有结果。

## 九、上线前需要你确认的事项

技术选型和来源研究可继续，不必等你补全所有信息。正式每日运行前，集中确认以下四组：

1. 可工作的城市、是否接受异地/出差/海外或远程，以及英文工作能力和工作资格限制。
2. 20K 区间已明确；还需确认是否接受包含提成的 OTE、外包/驻场、创业公司与个人贡献者岗位。
3. 只用本地电脑，还是允许公开数据服务器，以及可接受的月度基础设施/模型预算和通知渠道。
4. 自动化权限先止于“收集+匹配+材料建议”，还是在验收后对指定渠道开放投递；后者需要另行确认。

本轮默认：中文社招优先、AI 优先、地域先不硬过滤但明确标注；不限制为汽车行业，也不假定你可在任何国家工作；不启用投递。
