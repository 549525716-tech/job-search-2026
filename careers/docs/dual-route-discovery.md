# 双路线岗位发现与扫描规则

版本：2026-09-11-v2。配套配置：`../config/discovery-policy.json`。新增[行业分层与来源准入](industry-tiers-and-sources.md)：行业→细分赛道→行业大/中/小厂/地位待核→公司业务线→岗位。公司地位不是组织规模，分类补证不阻挡A/B采集。

**先形成行业与公司覆盖面，再从真实岗位学习招聘语言；同时用这些招聘语言搜索市场，发现名单之外的岗位与公司。** 两条发现路线共用证据库和待办队列，但分别统计贡献，不能把一次公司名搜索视为全公司扫描。

本次只制定规则，不联网、不搜索、不启用定时，不修改简历或投递。既有JD只可用于设计参考，不宣称已核对最新招聘需求。本规则由项目Skill指导后续执行；自动行业扩展、关键词引擎、查询调度及覆盖统计尚未接入现有采集器，配置不代表功能已实现。

## 一、目标与不变边界

- 服务管理职责、长期To B能力与收入可预期性，AI优先而非只收标题含AI的职位。
- 主攻市场营销、销售/KA、商务/生态/渠道、销售及商业运营、销售管理；客户成功及业务型售前是相邻方向。产品经理排除；产品市场营销保留。FDE/工程交付仅非默认探索。
- 固定月薪至少人民币20K。未知、区间跨门槛、OTE、年包或奖金不判达标，但不因此从发现库删除。匹配分、学历缺口、个人暂不具备某项技能也不是采集前硬筛。
- 全国国内城市先不硬筛；总部不代替岗位工作地。海外地点、语言及工作许可分别标注。
- 本轮规则制定不授权未来自动启动。用户之后明确要求扫描时，再建立该轮清单和执行记录；定时、登录、材料及投递仍遵守原授权边界。

## 二、路线A：行业 → 公司 → 岗位 → 关键词

1. **确定行业和细分场景。** 从政策、真实采购场景、产品与付费客户证据发现行业；先回答谁付钱、解决什么问题、有哪些商业职能，不能只列政策口号。政策不是每条机会的必需条件，也不等于企业订单。
2. **形成公司底册。** 每个细分场景记录头部、腰部和新发现候选，注明主体、品牌、集团/业务线关系、产品、客户群、商业模式、官网和招聘归属。未核行业排名可先入候选，不能凭名气或融资称龙头，也不能等排名齐全才发现岗位。按赛道口径核收入、客户或市场份额等依据，不强凑前十。
3. **核验招聘入口。** 官网至ATS的归属链、社会招聘分类及来源访问状态必须记录。旧10家种子与上一轮20家公司仅为起点，不是白名单或数量上限。
4. **扫公司岗位。** 可读全量目录优先遍历；有站内分类/搜索时，覆盖主攻职能及相邻职能，至少区分标题检索与正文检索能力。名称同义词、中英文和职责短语分别查询，不把几十个词同时AND。逐页记录游标、页数、原生总数、终止标识与候选详情完成度；不支持正文检索就显式标记，安排路线B补充，不能声称正文已扫。
5. **从JD学习关键词。** 对已取得完整职责和要求的样本提炼名称、业务内容、产出指标和门槛，保留原文引用。不同公司/岗位层级分别比较；单公司特有要求不得升级成行业共性。

第一轮行业研究框架暂含：基础大模型与开放平台、云/算力/AI基础设施、数据与AI开发平台、企业软件与营销数字化、AI企业应用、汽车与智能出行数字化、制造/工业智能化、机器人与智能硬件。它们是可修订的研究分组，不是本轮已验证的最新利好行业或确定排名。金融、医疗、能源等新垂直机会可经路线B进入，不受这8组限制。

## 三、路线B：关键词 → 市场岗位 → 新公司 → 行业归档

1. 使用路线A中提炼并审核的关键词，加上明确标为启动假设的名称词，建立版本化词库。
2. 不限既有公司名单搜索。名称词与职责词形成两支：既找“叫什么”，也找“负责什么商业结果”。行业词可辅助精准搜索，但要保留不含行业词和不强制AI字样的查询，避免漏掉新赛道。
3. 取得岗位后核对招聘主体、原文、地点、日期和来源。搜索摘要只能作线索；聚合页或公司页不能冒充职位直链；招聘顾问、外包、代理与实际雇主分别标记。
4. 新雇主经核验后进入公司底册，触发路线A的公司岗位补扫。未验证官网的公司留在待核池，不直接自动导航任意域名。
5. 新JD产生新词或旧词的新含义；记录为候选变更，由GPT-6审核后启用到下一发现波次。不因新公司行业未归类而丢弃岗位。

**冷启动分支：若A暂时没有取得可用完整JD（例如种子招聘站均受限），B无需等待A成功。** 可以使用明确标注的启动名称词、旧样本参考词及经GPT-6检查歧义的推测别名，在预先声明的批次预算内探索；这些词不算最新需求证据。B取得新完整JD后再交GPT-6提炼实证词，并核验新雇主、回补A。缺少真实JD时，不生成共性词结论或个人完整匹配。

**闭环：A提供可靠样本和招聘语言，B扩大召回并反向补充A。** 每轮冻结初始范围；运行中新发现的公司与新词记入下一波待办，不静默扩成无限递归，也不静默丢弃。

## 四、关键词提炼标准

| 词层 | 提炼内容 | 示例，仅作设计演示 |
| --- | --- | --- |
| 岗位名称 | 原生标题、同义称呼、职级、英文缩写 | 大客户经理、行业销售、Business Builder、Partnerships、Sales Operations |
| 客户与场景 | 服务谁、哪个业务环节、客户购买什么 | 企业客户、汽车商户、渠道伙伴、销售数字化 |
| 工作内容 | 有辨识度的动作、对象和责任 | 渠道招募、客户分层、商机预测、决策链、合同谈判、续约增购 |
| 业务产出 | 组织为哪些可验证结果付费 | pipeline、收入目标、回款、续费、客户使用率、团队产能 |
| 管理与协作 | 带人、预算、资源与跨部门决策 | 招聘、绩效管理、团队辅导、区域经营、资源配置 |
| 技术与门槛 | AI/软件场景、经验、采购或交付要求 | API、RAG、Agent、POC、SaaS、云采购；仅说明JD需求，不代表个人已有 |

- 每条词记录 `term_id`、原词、规范词、类型、语言、语义组、适用职能/赛道、歧义、正反例、证据和审核状态。
- 证据至少含公司、岗位ID、标题或正文出处、连续原文、来源链接、原文SHA、发布时间语义及实际观察时间。不得用模型改写短语冒充原文词。
- 状态区分 `bootstrap_hypothesis`（启动假设）、`historical_reference`（旧样本参考）、`observed_niche`（单家公司已观察）、`shared_verified`（至少两家独立雇主重复出现并经审核）、`inferred_alias`（推测近义词）、`retired`（停用但保留历史）。单公司高价值新词可小范围探索，不必等两家公司凑齐；只有共性结论需要跨公司证据。
- 频次按去重后的独立雇主与岗位计算，并附分母。转载、集团同岗、多城市复制不算新的独立雇主；词频不是录用概率，也不自动代表全行业高频。
- “沟通能力、责任心、团队合作”等泛词不单独生成查询。BD、KA、GTM、Agent、运营、增长等歧义词需商业语境；不得把“沟通”当销售、把“经理”当带人、把提到产品当产品经理。
- 中英文别名不自动互相等价。AI相关词与通用商业词分层，不能要求每条岗位同时命中所有维度。
- 硬性条件、优先项、职责与推断分开。陌生标题但正文有明确商业责任，先进入人工/模型复核队列；既有 `role-policy.mjs` 主要按标题分类，不能把其未命中当作新版正文召回已完成。

### 查询编排

| 查询方式 | 模板（非本轮真实搜索） | 目的 |
| --- | --- | --- |
| 公司站内/域名 | 已核招聘域名 + 单个职能名称/别名 | 扫已知公司及其不同岗位称呼 |
| 名称精准 | 原生岗位名 + 招聘，可加行业或城市 | 找同名/近似岗位 |
| 内容精准 | 辨识度职责短语 + 一个商业场景词 + 招聘 | 找标题不直观的岗位 |
| 名称拓展 | 同义名称 + 招聘，不指定公司 | 发现新雇主 |
| 内容拓展 | 一个高辨识度内容词 + 招聘，减少行业限制 | 防止原公司样本把搜索锁死 |

不要求搜索站点支持同样的布尔语法、引号或正文搜索。记录实际发送的查询及站点能力；零结果可在不触发限制的前提下拆词、换语言、去掉行业限定。至少保留精准/拓展两档的完成或未执行状态；预算不足时标待续，不能把“已查1次”记为覆盖完整。

## 五、信息来源与时效

两条路线是发现逻辑，不是只有两个网站。官网/官方ATS负责主体和JD；招聘平台补充岗位及薪酬；认证招聘公告、公开招聘活动或公众号作为发现线索；搜索引擎负责跨站召回，不能代替招聘站完整列表。每个来源受其登录、访问与可验证能力约束。

具体渠道、用途和准入字段以 `../config/source-catalog.json` 与[来源规则](industry-tiers-and-sources.md)为准；先形成实际入口清单，再安排A/B查询。该目录不解除既有访问限制，也不表明所有列出的ATS/招聘平台都已实现。每轮覆盖增加“赛道×行业地位×路线×来源状态”，地位待核单列，不改变冻结分母或重复计同岗。

- 仍受限的BOSS、猎聘、MiniMax等不因换路线就自动恢复，也不通过换浏览器/代理规避。官网上独立可用的信息可以采集，但不能冒称取得了被限制平台的内容。
- 下一次扫描时优先核对当时可用的正式社招列表/详情。最近90天明确发布的岗位优先，其余无日期但仍可公开找到的岗位可保留；90天是检索排序窗口，不是过期判定。旧日期不自动关闭，无日期不伪造为新发布。
- 分开记录发布时间、页面更新时间、首次观察、最近观察、申请开放证据与核验时间。搜索索引抓取日期、本机文件mtime、报告生成时间都不是岗位发布日期。
- 最新招聘词库必须标明本轮JD样本范围与核验日期。旧样本可帮助启动搜索，但未重新核验不能宣称“最新市场标准”。过往政策与行业排名同理。

## 六、统一记录与去重

后续执行以独立运行目录保留以下逻辑表；没有真实数据时不生成假清单或假执行回执：

| 逻辑表 | 必需内容 |
| --- | --- |
| scope | run_id、路线版本、词库版本、截止时间、初始行业/公司/查询单元、允许来源、阶段预算、未覆盖范围 |
| industries / companies | 身份与别名、关系、赛道、商业需求与分层证据、归属核验、发现路线、状态、复核日期 |
| keywords | 原词/语义/证据、独立公司与岗位计数、状态、审核者、版本、失败查询反证 |
| query_tasks / calls | route、query_id、company_id或term_id、源、真实查询、过滤项、页码/游标、开始结束时间、结果证据、状态及续接点 |
| jobs / observations | 原生ID、公司/品牌、标题、原文、地点、薪资原文和构成、链接、时间语义、完整性、来源、发现链 |
| frontier | 新公司/新词待办、未执行/失败/分页待续/提取待做、原因、优先级、下一可执行动作 |
| assessments | 直接证据/可迁移/缺口、门槛、固定薪核验、管理权、分析版本；不覆盖原始观察 |

同源优先按雇主与原生岗位ID去重；无原生ID时才组合主体、业务线、标题、城市与正文特征作为疑似同岗。公司总页不能作为岗位唯一键；跨平台只建关联，薪资/城市/原文冲突分别保留。保留所有 `discovered_via`，统计A独有、B独有、共同命中和B新增公司，不能因为去重删除路线证据。

## 七、覆盖与停止规则

- **不设“扫20家公司”或“抓25条岗位就结束”的全局上限。** 分批是调度方式，不是缩小市场定义。GPT-6每个分析批次最多20个新增/变化候选；其余进入待分析队列，采集不因此停止，也不自动无限循环分析旧岗位。
- 执行前冻结本批公司/查询单元和时间/请求预算并展示；预算用于暂停和续接。首批可分片执行，不能未经说明自行把本批范围当成全部行业或市场范围。
- 来源状态至少区分：未扫描、检索完成但未读详情、部分列表、分页待续、详情缺失、来源范围已完整读取、真实空结果、访问受限、技术失败、明确关闭。
- **只有官网/ATS声明范围内的分页已到原生末页、数量可对账且相关详情无缺失，才可标该来源范围完整。** 关键词过滤结果完整也不等于全公司完整。第三方搜索结果读完只能标该查询已执行，不能标全公司/全市场覆盖或没有岗位。
- 真空结果需在访问成功、范围明确、无截断/无加载失败且有原生0结果证据时成立。受限、超时、只搜索未命中、无正文、停在第一页均不算空。
- 覆盖率分别报告：已核公司/公司底册、已尝试公司/冻结公司、完整来源范围/计划来源范围、查询执行/计划查询、完整JD/待提取候选。分母必须版本化；发现新公司放下一波，不偷偷缩分母。未知市场总量不计算全市场覆盖率。
- 某一波清单处理完且新发现已入下波队列，可称“该波已处理”，不是“市场扫完”。若边界内全部合法可访问来源都完成、受限及未访问源已列清，称“声明范围扫描结束，仍有X受限/待续”，不能把受限当完整。
- 全部主动搜索/导航共用队列，完成后间隔10–20秒，更严格要求从严。先记真实开始时间，返回后保存真实结束时间、请求、响应级别与hash；时间丢失就标审计缺口，不以落盘时间补造。
- 验证、登录墙、401/403/429或访问拒绝首次即停该源。一般技术根因最多3轮修复验证，再失败则隔离留待办；不是每家公司默认尝试3次，更不是反复刷新授权。

## 八、角色与执行顺序

| 角色 | 模型 | 输入 → 输出 | 判断与依赖 |
| --- | --- | --- | --- |
| 产业/公司资料执行 | Luna / medium | 研究分组、已有证据 → 行业/公司事实与待核入口 | 整理原文，层级/政策利好不能自定；由总控/GPT-6作重要判断 |
| 岗位扫描执行 | Luna / medium | 冻结A/B任务、访问策略 → 逐条来源回执、JD、发现关系、待续点 | 共用单一联网队列；不自行把新词或推荐结论定稿 |
| 需求与关键词分析 | GPT-6 Astra / max | 完整JD及证据 → 标题/内容词库、语义边界、查询扩展规则 | 先有证据再提炼；旧样本、推测同义词单独标识 |
| 个人匹配与取舍 | GPT-6 Astra / max | 候选JD、个人事实、偏好 → 直接/迁移/缺口及核实顺序 | 每批≤20；不因个人缺口缩掉整个采集词库 |
| 独立检核 | GPT-6 Astra / max | 冻结结果、来源和分母 → 漏扫、误召回、归属/薪资/时间审查 | 未参与对应实现；不把测试通过等同市场覆盖 |
| 总控与确定性处理 | 当前Codex + 本地程序 | 各输出 → 合并文档、去重、进度、下一波 | 固定处理不新增LLM API，记录真实模型/档位/ID，不报虚构Token节省 |

常规扫描顺序：冻结方向与范围 → 行业公司发现 → A取得首批完整JD → GPT-6审核关键词 → B精准/拓展检索 → 新公司回补A → 合并去重与分批匹配 → 覆盖审查及报告。若A无可用JD，转第三节冷启动分支：B用已标假设的词先探索，得到真实JD后再回到实证提词流程。A剩余采集与已审核词的B任务可以交错调度，但网络仍串行；不同角色的文件写入范围分开。

## 九、下次执行验收

交付一份综合报告，同时附行业/公司底册、名称/内容词库、岗位表、A/B贡献对比与未扫清单。岗位正文、薪酬、地点、链接可回查；固定薪未知不会消失，陌生标题能从正文进入待核，产品经理不会因关键词命中混入推荐。
