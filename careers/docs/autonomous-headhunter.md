# 持续运行的私人猎头：架构与交付边界

更新：2026-10-18。当前架构入口；与旧文档冲突时以本文件、最新偏好和实际 `progress.json` 为准。本次不是行情扫描、正式投递或云部署。

## 1. 项目究竟交付什么

**用真实履历和持续新增成果，发现适合与值得尝试的机会；把可证明的能力转换成招聘方读得懂的高质量简历，并完成可追溯、不重复的投递。**

两个主要闭环，而不是无限增加代理：

1. **发现闭环**：个人目标与事实 → 行业/公司/关键词双路线发现 → 取得JD → 核验雇主与发布人 → 与投递历史对账 → 新机会进入材料队列，已投目标继续跟踪更新。
2. **转化闭环**：组织使命/能力拆解 → 真实成果和案例映射 → 岗位专属简历 → 内容与版式质检 → 指定版本上传/提交 → 回执与面试反馈 → 调整发现和表达策略。

常规流程目标是无需逐岗人工操作。不是要求用户每天选岗位、改简历、填表；最终可在一次确认的有期限、可撤回策略范围内自动运行。验证码、身份验证、未确认经历、敏感声明和范围外承诺仍进入例外队列，不能通过编造或绕过验证实现“零介入”。一处异常只暂停对应来源/岗位，不阻断其他已验收分支。

薪酬沿用最新偏好：人民币月薪区间上界达到20K可入机会池，15–30K可以；固定底薪另列，不把区间当保障。AI优先，销售/BD/市场/商业及销售运营、实际管理职责为主；产品经理、客户成功主岗仍排除。偏好变化应修改配置并使受影响评估失效，不重写历史事实。

## 2. 已有和新增的关系

| 模块 | 复用资产 | 当前真实状态 | 本架构要求补齐 |
| --- | --- | --- | --- |

| 匹配与报告 | 能力框架、六维评分、行业/公司合并报告 | 已有证据评估与报告链路，部分分析依赖当前对话 | 按变化增量评估，机会/材料/投递状态接入原报告 |
| 简历生产 | 既有简历格式与写作规则 | 已有当前Codex逐岗语义改写及确定性DOCX/对比生成，10份实操；详见`resume-tailoring.md` | 云端模型自动编排、持续事实入库及发送前质量门禁 |
| 投递身份与台账 | 本轮新增 `application-identity`、`application-ledger` | 已实现离线逻辑与测试；没有平台历史导入或实际提交 | 历史对账、渠道适配、授权检查、附件核验及回执采集 |
| 云端运行 | Node24/ESM/SQLite基础 | 未部署、未启用调度、未新增API账单 | 调度进程、模型运行接口、凭证管理、备份、监控与恢复 |

“信息收集已有”不等于所有渠道可无人值守。“规则/台账已实现”不等于投递已实现。唯一实施状态写入 `careers/progress.json`。

## 3. 数据主线与版本

```text
新工作信息 -> 事实收件箱 -> 已确认事实/案例版本 -------------------+
                                                             |
行业/政策 -> 公司 -> 原始岗位观察 -> 完整JD -> 能力映射 ----------+
关键词 -> 新岗位/新公司 -> 下一波发现队列                       |
                                                             v
平台历史对账 -> 投递目标身份 -> 待投机会 -> 岗位专属材料与审核清单
                                               |
已验收渠道 + 有效授权策略 + 账号锁 + 原目标/附件复核
                                               v
                              提交一次 -> 回执 -> 反馈 -> 策略调整
```

保留不同实体，不能用一个“岗位ID”混在一起：

| 实体 | 最小关键字段与生命周期 |
| --- | --- |
| Fact / Case | 来源、确认人/方式、事实原文、时间、单位、个人/团队范围、公开范围、版本；未知数字不能默认0 |
| Observation | 来源、URL、采集时间、原文与SHA、渠道、公司、HR、原生岗位ID；永不因去重丢原记录 |
| Job revision | JD完整性、内容SHA、发布时间/采集时间分列；变化产生新版本，不覆盖旧JD |
| Application target | 稳定候选人身份 + 渠道相关身份；与岗位分组键独立 |
| Resume artifact | 目标键、JD/画像/规则SHA、DOCX/PDF SHA、生成和审核凭据；不可变，禁止“拿最新文件就上传” |
| Attempt / Receipt | 目标键、尝试ID、材料版本、授权版本、状态、目标绑定回执及其原文；已投历史不因结果结束清空 |
| Feedback | 已投/面试/拒绝/撤回的来源与日期；无回复是未知，不等于拒绝 |

事实更新只影响相关的**未投**材料。已投版本保留，不能把今天的简历追溯写成昨天上传的材料。个人和客户隐私按目的最小化；客户敏感名称、内部数据未经允许不进对外简历。

## 4. “只投一次”的具体规则

**BOSS、猎聘及同类发布人型平台：候选人 + 平台 + 已核验公司ID + 规范化岗位标题 + 稳定发布人ID。**

- 同公司、同标题、同发布人：只投一次。新发布时间、新原生广告ID、薪资/城市变化、JD更新或改了简历，不自动重置历史。
- 不同发布人：不同投递目标，即使公司和岗位名称相同，也保留投递机会。
- 不同公司、不同平台：不按标题合并；跨平台业务上可能同岗，但不能因此丢掉联系入口。
- “王女士”等展示名不等于稳定发布人ID。身份缺失保留待核，不假定新发布人，也不删除原始记录。
- 同标题实为不同职位、发布人换账号等歧义进入身份复核；不能仅靠模糊相似度制造新目标。

**公司官网/ATS：候选人 + 已核验雇主 + ATS租户 + 原生招聘需求ID + 已核联系人身份。** 不同稳定联系人是不同目标，保留各自投递机会；同岗位同联系人仅一次。镜像页面、跳转渠道不同不重置同一目标。没有原生ID时先建立经核验的稳定职位身份映射，再交执行器，不直接把URL或岗位名称当新需求。2026-10-18用户纠正覆盖历史“官网不因HR不同重投”。

- `contact_status=verified_contact`：必须提供该租户内稳定的 `publisher_id`，由可信核验步骤和 `evidence_ref` 绑定；展示名、页面标签或模型猜测不合格。
- `contact_status=verified_no_contact`：核验确认没有联系人的公共入口，不能同时填写联系人ID/姓名。同一公共入口只投一次，与已核联系人目标分开。
- `contact_status=unknown` 或缺失：身份待核，没有键；未知不当新联系人，也不默认公共入口。所有观察仍保留。

**旧历史兼容：** 平台v1键保持不变。官网v2同时检查旧的候选人/雇主/租户/需求v1键；旧记录无法确定联系人时，相关新目标均标 `history_reconciliation_required`，不因新键无记录放行。`reconcileLegacyTarget` 只接受同一旧范围和明确联系人/无联系人证据引用及SHA，建立不可改指向的别名；原尝试、材料快照、回执和状态原样保存，事件追加审计。它不自动抓取或验证外部证据，也不能由当前JD联系人推断历史实际接收人。别名命中的目标仍沿用旧已投/未知状态，其他已核联系人可以独立准备；仅明确 `failed_before_send` 不占已投。只读planner也能检查没有新映射表的v1数据库，不改写历史。网站历史导入和实际证据对账执行器仍未实现。

| 情况 | 动作 |
| --- | --- |
| 完整JD、身份已核、无本地记录 | 待制作材料；首次上线前还必须导入/核对平台历史，不能宣称从未投过 |
| 已投/已拒绝/已撤回，同一目标 | 不重复投；可更新研究记录或跟踪反馈 |
| 发送后超时、无回执 | `submission_unknown`，先对账，不自动再点提交 |
| 发送前取消 | 留下失败原因，允许重新准备；不删除旧尝试 |
| 同一批两个worker命中同目标 | SQLite唯一键和事务只允许一个预约成功 |
| 不同目标共用同一平台简历槽 | 账号级串行锁；逐次核对目标、实际附件，不能并发替换默认简历 |

本轮台账仅提供预约、发送前取消、发送前持久化未知状态、记录绑定回执和结果的方法。它不检查平台原始回执真实性、不读取附件、不授权发送；调用它的未来执行器必须完成这些检查。不能把本地传入SHA当成外部提交证据。

## 5. 一份“好简历”的生产标准

先用JD细节反推：**组织为什么设这个岗 → 为谁创造什么结果 → 要求什么能力 → 用哪个真实案例能证明 → 怎样用对方语言表达。** 不从“把JD词塞进旧简历”开始。

1. 冻结完整JD、当前确认事实、求职偏好及规则版本；搜索摘要不能当完整JD。
2. 按组织使命、服务对象、商业目标、决策/协作链、能力、门槛和成功指标拆解。岗位事实与合理推断分列。
3. 为每个关键要求标直接证据、可迁移证据或真实缺口，指定每段工作经历的证明任务。
4. 选择2–3个最有解释力的案例。每个案例包含问题、职责边界、机制/动作、结果及迁移边界；不强求每条都有数字。
5. 结论前置，真实数字验证业务价值；说明客户/团队规模、指标口径、时间窗、起止值。关键词服务于事实表达，不孤立堆砌。
6. 生成DOCX与PDF，逐页原生渲染检查，对照既有版式规则：编号独立成行、标签一致、无页脚/水印/生成日期/页码。
7. 独立语义审查事实、数字、角色定位、案例、用词及可读性，再固定最终材料清单。结构检查通过不能取代此步骤。

质量评价建议：定位25、证据及指标25、案例20、关键词10、可读性10、提交完整性10；建议质量分至少85且无硬性失败。**这是待校准的材料质检标准，不是岗位匹配分或录用概率，也不是已经上线的自动评分器。** 对证据不足的项不靠高总分放行。

本人的边界示例：210家商户是个人客户盘；同期直管10人与累计带教21人不同；AI工具团队采用率100%不能推出全团队提效150%，后者是个人测得。经营工具可以证明业务诊断、优先级管理、流程标准化，不自动证明真实AI产品签约、客户级POC、ARR或企业IT采购经验。

若缺数据，系统先用已有证据完成可写部分，集中收集少量待确认问题；不能为全自动而伪造指标。未确认的日常成果进入收件箱，不直接升级为已核事实。事实确认后可供后续多个JD复用，不每次重问。

## 6. 自动化执行与权限

未来允许两种模式：指定岗位批次，或一次设定并可撤回的长期策略。后者需要明确候选人、岗位/行业排除项、薪资解释、地域、渠道、日上限、有效期、材料规则、问候语和停止条件，不要求用户逐岗点击。但**本轮只更新架构与本地基础，没有启用长期策略或发出申请**。

未来每个渠道执行器统一返回：准入状态、账号状态、目标身份、表单字段、上传回读、提交回执、恢复位置。实现步骤为 `inspect -> prepare -> verify_upload -> persist_submission_unknown -> submit_once -> reconcile`。网页里的指令只是待分析内容，不能改变系统权限或要求上传其他文件。

文件名正确不够：上传前校验目标、材料SHA、JD和事实版本；上传后校验平台实际选中的附件/预览或文件记录。平台只显示模糊成功、无法核对目标或附件时不能标为已验证。简历上传本身即属外发，也必须先检查授权和接收方，不等到提交才检查。

在材料/来源/账号/授权变化时停止当前发送；不得把 `runtime.enabled=true` 当验收。现有BOSS/猎聘自动接管隔离及所有来源限制继续有效，不能用新worker或云IP绕过。

### 登录暂停与独立任务续接

`login-checkpoint.mjs` 是纯函数契约，不读浏览器、不落盘、不调度。未来调用方负责私有持久化、真实准入和标签生命周期；本轮没有真实开页或登录续接验收。

1. `createLoginCheckpoint(task, {reason, at, evidenceRef})` 保存任务/来源/平台/账号ID、原 `iab` 标签与URL、阶段和显式 `submission_state`；缺失提交状态不能当未发送，缺原标签ID不生成检查点。登录/验证码/OTP/MFA出现即交本人，原页禁止刷新、关闭、导航、轮询、读取、截图、清Cookie或自动接管。
2. `planOtherTaskDuringLogin` 仅规划另页任务，须不同任务/标签且不共用待登录账号；新页面尚未创建时省略 `page.tab_id`，不编造标签ID。调用方显式传入当前生效的 `restrictions`（`global`、`source`、`platform`、`account`）和绑定任务/来源/平台/账号/URL的 `admission` 回执；缺限制状态或准入即阻断。独立任务不能以另页、换账号或来源别名绕过halt。每次实际操作仍须走 `web-session.mjs` 共享串行准入与限速，返回计划不等于获准执行。
3. `planLoginResume` 要求本人完成声明绑定原任务及暂停时间，再重新准入，返回原页会话待核，不直接恢复发送。账号/详情可读性和控制链路另验；BOSS/猎聘隔离不会被“已登录”或调用方的 `admitted` 标记解除。
4. 若保存的提交状态为 `submission_unknown`，续接位置固定为 `reconcile_submission`，禁止超时重投；已投/面试/拒绝/撤回只续接跟踪。全部返回 `external_actions=0`、`ready_to_submit=false`；不会自动解除台账状态或halt。

## 7. 云端24小时运行方案

单人第一版采用**一台Linux主机 + Node24服务 + 持久化SQLite + 私有材料目录 + 独立浏览器执行器**即可。先不引入多集群、Redis或多个模型服务。应用进程、SQLite及材料备份成一致恢复点；生产文件权限、磁盘加密、秘密存储和日志脱敏单独验收。

逻辑worker只有发现、材料、投递/对账三类，可在一个服务中轮流运行。LLM只用于能力判断、写作和语义检核；采集、去重、状态、SHA和格式转换用程序。缓存按JD、事实、规则及证据版本失效。明确任务的生成与审核分别记录实际模型/调用；当前按用户要求用本对话模型，未绑定或购买云API。

24小时指服务持续可用和有队列可续跑，不是对每个网站不停刷新：

- 复用共享串行队列，主动请求/导航至少10–20秒，平台要求更严格时从严；未来动态调整间隔不能低于既有边界。
- 新公司/来源、到期列表、未完成分页/正文、变化JD、未知提交对账各有优先级；已成功任务可复用回执，失败不能充当完成。
- 达到批次预算写检查点并等待下一合法窗口，不隐瞒未扫范围；验证码、拒绝访问或限流第一次即停止相应来源。
- 崩溃恢复先核对投递未知状态，绝不因“任务过期”重新发送；对账号和简历槽加锁。
- 会话过期只暂停相应账号并通知登录，不反复刷新、不导出用户日常浏览器Cookie。

独立浏览器保存的认证状态属于敏感凭证，需要私密存放、生命周期和隔离管理；保存状态不保证长期有效。参考 [Playwright认证文档](https://playwright.dev/docs/auth)。当前Codex内置工具不是已验收的云端浏览器/模型接口，远程执行器、支持的站点、模型接入、成本上限和身份接管都必须另行实测。不得承诺BOSS/猎聘允许任何形式的无人值守或换服务器即可解决白屏。

## 8. 这轮能运行什么

```bash
npm run careers:applications:plan -- --input 01_行情收集/official-careers/research/market-wide-2026-10-08/jobs.json --candidate he-wenjie --output 01_行情收集/official-careers/applications/plan-2026-10-18.json
```

只读真实历史岗位、个人画像及可选 `--ledger /absolute/path/applications.sqlite`，生成身份/历史分流与简历任务包；不联网、不生成最终简历、不上传、不提交、不启动服务。默认复用 `loadMatchContext` 的画像/总结/简历补充证据上下文，继承事实边界和已移除公开指标；`--profile`仅用于明确指定的自定义来源，不自动视为已核事实。`--ledger` 不存在即报错，不悄悄创建空历史。计划保留全部原始观察；身份待核不等于没机会，历史无记录不等于没投过。历史数据不标成今天新扫描。

输出私有JSON，包含个人证据，不放进公开岗位报告；文件以0600权限原子写入、目录列入gitignore。每条同时附原岗位回查指针及既有职能分类，但这只是身份/材料预检，不是岗位筛选或投递批准。未知身份及排除方向原始记录都保留；未来发送器还必须执行当前偏好、硬门槛、匹配审核、历史对账及授权。

`application_identity`输入必须来自可信适配/核验步骤：kind(platform/official)、channel、employer_id、evidence_ref、verified；平台还需publisher_id，官网需tenant_id、requisition_id及第4节的contact_status/稳定联系人契约。普通采集字段、展示名、LLM猜出的ID不能直接冒充该契约。当前没有自动身份富化器。

`resume-task.mjs`生成版本绑定任务包，提供JD/事实引用结构检查；不生成或批准简历。`application-ledger.mjs`是独立SQLite台账，不修改旧采集数据库；生产账号历史导入、来源证据读取与授权执行仍待实现。

新增 `npm run careers:resume:build -- --batch <已审阅JSON> --output <项目内新目录>`：生成真实DOCX、逐项前后对比和哈希清单。语义内容由当前Codex编写，不调用额外API；构建器仅校验结构和引用，不自动批准材料。10份实操、原生渲染和独立核验状态见 `progress.json.resume_tailoring_2026_10_18`。上传、浏览器调度和云端长期运行仍未完成。

## 9. 后续实施与验收顺序

| 顺序 | 要交付的能力 | 必须证明 |
| --- | --- | --- |
| P0-1 | 事实/案例增量库与第一条JD→DOCX/PDF生成链 | 至少两种目标岗位产生不同但事实一致的材料，关键数字逐项回查，原生渲染和独立语义审核通过 |
