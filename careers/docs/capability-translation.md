# 能力反推与案例转译

生效：2026-09-16。本文件覆盖旧的固定底薪筛选、强制公司分层和只按JD词面匹配规则。适用于所有岗位，不只销售；不扩展投递、登录或定时授权。

## 核心链路

**先了解本人事实；再从JD细节反推岗位使命和能力框架；在框架上匹配真实经历；最后用招聘方的业务语言呈现可举证案例。**

1. 从JD提取原句、服务对象、工作场景、职责边界、产出、成功指标及硬条件。分开页面标签与正文，冲突不自行消解。
2. 反推组织为什么招这个人、要解决什么业务问题、买什么能力。岗位名称不直接决定能力或职级；未知角色先研究多个代表性JD。
3. 定义能力维度和子项，再根据JD主责分配权重。不能先看用户强项再调高对应权重，不能把不同公司个性要求误称行业共性。
4. 对每项能力核对用户案例的场景、动作、结果、职责和证据。直接证据、强/部分迁移、已知缺口、未知分开。缺乏同行业履历不等于没有相同底层能力。
5. 写清迁移桥梁：相同的业务机制是什么、客户/产品/决策链差异是什么、已有案例能证明到哪里、还缺哪份材料。缺口分“证据没呈现”“相邻能力需迁移”“确实没有经历”三类。
6. 按“能力结论 → 真实案例 → 方法与关键动作 → 可核结果 → 可复用资产 → 迁移边界”组织定向简历。缺失重要事实集中提问，不靠同义改写把未知写成已完成。
7. 10秒阅读检验：看得出候选人定位、问题复杂度、系统方法、组织价值及证据归属；不能只剩工具清单和孤立数字。

### 实际例子：钛动销售管理

JD的目标拆解、归因、客户分层、PDCA和工具需求，背后买的是“让销售组织可诊断、可干预、可复制的经营能力”，不只是做报表，也不能由标题推定人事管理。

可转译案例：主导区域目标拆解、经营复盘和分工督办，以商户商业消耗、线索与转化定位经营问题；把优先级和商户动作沉淀成客户地图及车型分析工作流，供团队使用。

边界：210家是个人客户；区域协同不是人事直管；AI工具团队全员采用但150%效率为个人测量；未证明产品规则改造上线。它证明经营机制和业务系统化能力，不证明企业级产品/数据治理成果。

### 实际例子：MiniMax技术销售

“技术Demo、POC、AI成熟度和ROI场景”反推为“以技术验证降低客户采购不确定性并推动采用”。用户经营诊断和AI工具是相邻场景能力。云/MaaS三年销售和客户POC是现有事实缺口；独立技术Demo能力目前未充分举证，应询问确认，不能认定不会。JD未限定必须API Demo。不能继续套旧版普通KA的匹配结论；演示项目可补材料，但补不了真实任职年限。

## 可解释评分

规则：`careers/config/capability-rubric.json`；确定性计算：`careers/capability-scoring.mjs`。

- 六个能力维度：目标与商业结果、客户与行业场景、问题诊断与方案价值、项目协同与经营机制、产品技术与系统能力、增长验证与方法复制。
- 每维下按实际JD拆子项，子权重合计100%；维度权重也合计100%。销售运营默认20/15/25/20/10/10，技术销售15/20/20/15/25/5；非适用岗位可另定权重并解释。
- 子项锚点：同类完整100、同类部分80、强迁移60、部分迁移40、已知缺口0、未知0。锚点是人为制定的透明证据标准，不是统计学预测；“完整”仍是现有本人陈述的完整，不等于第三方背调。
- 维度得分＝Σ（子项分×子权重/100）；总分＝Σ（维度分×维度权重/100）。未知所占权重另列，不能把未举证解释成没有能力。
- 硬门槛逐项列已满足/未满足/待核，总分不能抵消；学历、年限、特定产品经验和核心交付要求不可省略。80分不等于面试概率，也不自动允许简历沿用或投递。
- JD、个人画像、规则或偏好改变，旧评分不沿用。旧匹配库的粗粒度覆盖分是历史口径，不与新版复合分直接混排。

## 薪资和展示

用户2026-09-16口径：优先薪资，其次岗位匹配。一线销售、经营分析与管理均可尝试。人民币月薪区间上界达到20K即可进入机会池，如15–30K；固定底薪、奖金、提成、试用期及保障条件单列待核。未知、年包、外币、OTE不推算补齐。

先分可比较薪资机会池/薪资待核/已知低于目标，再按能力分排序；另提供薪资区间下界排序。公司相邻展示，不改变原始观察或联系入口身份。未经核验的同名记录只能做展示聚合，不继承该公司法律主体、公司标签和评分。

公司卡片需要法定主体/品牌关系、行业/业务线/产品与客户、人数区间、融资/上市、资质标签、地点、原文来源、日期和核验状态。来源冲突并列；平台/自述/用户补充/官方资质核验不可混同。

大中小厂暂列低优先级待办。超过100家可回查且身份已核的不同雇主后，在报告提示用户讨论标准，先分析样本分布和来源缺失，再提出标准；不自动分类。历史种子156个名称不是156家已核公司，也不因此提前触发。

## 关键词与持续扩展

`keyword-axes.json`列行业产业链、趋势政策、公司品牌产品、岗位名称、客户场景、职责方法、业务结果、管理协作、技术门槛、商业模式十轴。保留原句、来源、日期、公司身份与JD完整度。一个公司多入口不能被算成跨公司共性；未命中的“十五五”等只是研究假设，不是已核政策结论。

A：行业/需求→公司→岗位→证据词；B：证据词/明确标注的启动词→新岗位/新公司/招聘入口→回补A。每次按业务场景与职能组合扩展，陌生标题仍读正文；排除职能不删除原始观察。公司分层不再阻碍发现或展示。

## 固定执行入口

`npm run careers:decision:report`离线重建HTML/CSV/Markdown/JSON。配置`capability-review-input.json.sources`指向实际样本；定向评估按新JD追加，不重复开发。`context_sources`绑定画像、偏好和评分规则，变化即失效；每项JD哈希单独绑定。

当前版本整合111条历史观察、6个完整JD入口和46条线索；有重叠，不作为独立职位总数。6个入口/5个岗位方向已评分，其他候选未评分。当前只是这些既有样本的重组，不是新增扫描或全市场完成。下一波查询写入报告，只有实际执行并保存证据才改为已搜索。

常规执行默认单主线程＋程序解析，明确资料任务有需要才用快速模型。重要规则改动用一次独立复核，不为每轮日报重开多人团队。定向简历和投递仍需用户选择岗位并授权。

## 报告的行业漏斗

报告默认按行业 → 公司 → 原始岗位观察展示，展开到公司；“收起全部 / 展开到公司 / 全部展开”只改变展开层级，不删除数据或合并联系入口。公司和行业可单独折叠；搜索时展开命中的公司，清空搜索恢复原折叠状态。薪资与能力排序在行业内执行，统计随筛选变化，不随折叠变化。

行业来自已保存的公司行业或岗位业务分类字段；缺失或存在跨行业冲突时显示“行业待核”，不靠公司名字猜测，也不等于完成法律主体核验或大小厂分类。

后续采集沿用同一个报告，不另建页面：在 `capability-review-input.json.sources.additional` 追加 `{jobs, run}` 文件引用即可。旧数据、日期、原文SHA和评分全部保留，新JD未评估时明确待评分。报告生成是离线步骤，不能把生成时间当采集时间。当前仍为按请求执行，未启用自动定时；每批留存实际请求、成功详情、失败/受限和待续链接，不以单轮耗时宣称全市场完成。
